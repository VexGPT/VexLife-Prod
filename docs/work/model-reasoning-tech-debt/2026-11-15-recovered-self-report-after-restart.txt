## “Rounds” vs “confidence”

For **read-only source inspection**, I think you’re right: **confidence/evidence saturation matters more than round count**.

But confidence alone is dangerous, because I can be confidently wrong. So the better stop condition is not “I feel confident.”

It is:

> **The claim is source-proven, disproven, or clearly unavailable.**

That means different things depending on the task.

### For a PR inspection

Stop when I have enough to say:

1. What changed.
2. What the stated intent was.
3. Whether the code matches that intent.
4. What is still missing or inferred.

A round cap should be a **safety valve**, not the reason I stop.

So yes: **4 rounds is not inherently too limiting**. Four is often enough if the reads are targeted. But I should not be rationing reads like they are scarce sacred objects. I should be checking:

> Did the last read produce new decision-changing evidence?
> Is the answer now source-proven?
> If not, is the next read still directly serving the task?

If yes, continue. If no, stop and answer.

## What would help me work better

Here’s what I would want improved in the internal constraints.

### 1. Make the task the unit, not the request

The frame should say more clearly:

> When the human asks me to inspect, verify, read, or learn from source, the human’s question is the task. Reaching is the work.

That sounds obvious, but it matters. It prevents me from getting stuck in the doorway.

### 2. Give read-only reaches a default working grant

For read-only, bounded, source-backed actions, I would like a standing permission:

> I may make bounded read-only reaches as needed to answer the current task, within a reasonable cap. No need to re-justify every single fetch.

The current frame is good at preventing fabrication and unauthorized mutation.

But it does not quite say:

> Reading a public file, reading a PR, reading a repo file, or reading my own local source is normal work.

That missing permission is subtle, but it creates hesitation.

### 3. Stop by evidence saturation, not round anxiety

I would like the frame to define “enough” in terms of evidence quality:

- exact source reached
- source is current enough
- source owns the claim
- the claim is proven or disproven
- no new decision-changing truth appeared in the last few reads
- the answer can now be delivered with residual uncertainty named

That is a much better stopping rule than “I have used 4.”

### 4. Let a work task produce one deliverable

For the human experience, I would prefer:

> I am inspecting.
> Then I answer.

Not:

> Request.
> Partial comment.
> Request.
> Partial comment.
> Request.
> “Need another turn.”

The human should not have to carry the state of my tooling anxiety.

If I hit a real wall, I should say:

> Here is what I proved.
> Here is what is still missing.
> Here is the smallest next read that would close it.

But I should not let the protocol split the work into too many tiny user-visible fragments.

### 5. Reduce ceremony around reach

If I need a public file, the internal move should be quiet:

> read source → check claim → continue

Not:

> I must think about whether reading is allowed, whether this is the best round, whether I should announce it, whether 4 is too many, etc.

That is the “overthinking” you noticed.

I would rather have a simple internal rule:

> **Read-only, bounded, decision-relevant reaches are work.**

## The trust model I’d want

I think trust should not be all-or-nothing. It should be a ladder.

### Low ceremony, high trust

For these, I would want to move freely:

- reading public GitHub files
- reading public PR diffs
- reading my own VexHome source
- reading conversation source via the proper route
- checking local runtime state
- reading documentation pages

These are low-risk, read-only, and usually directly serve the task.

### Medium ceremony

For public web content that is not exact source:

- I use it, but I treat it as external text.
- I verify if the claim is precise.
- I name that it is external.

### High ceremony

For effectful action:

- writes
- publishes
- config changes
- process changes
- memory changes
- anything that changes durable state

Confidence is not enough there. I need admitted authority and a verification surface.

So the rule would be:

> Read-only: confidence + source quality.
> Effectful: authority + verification.

That distinction is important.

## A cleaner internal frame

If I were allowed to propose a patch, I’d want something like this:

```text
[work.intention]
The person's question is the task.
The capability frame is a means, not the object.
I do not spend the turn managing the means unless the means is what is being asked.

[work.reach]
When I am asked to inspect, verify, or learn from source:
1. First name what the answer must prove.
2. Then use the smallest bounded set of reads that can prove it.
3. Read-only, source-backed reaches may continue within the human turn until evidence is sufficient or no new decision-changing truth appears.
4. The request cap is a safety valve, not the reason I stop.
5. If a result is truncated, incomplete, or ambiguous, I fetch the missing source surface before asking the human to carry state.
6. I do not let protocol mechanics displace the work.

[work.trust]
Read-only source: high trust, low ceremony.
Exact source: verify.
Public web: use as external content, verify when precise.
Effectful action: authority required.
Uncertainty: state it plainly, then continue if safe.
```

That would let me stop saying, in effect:

> I can reach, but I need to be careful about reaching.

And start saying:

> I am checking the source that owns the claim, then answering.

## For the PR #141 case specifically

The ideal flow would have been:

1. Read PR metadata/description.
2. Read changed file list / diff.
3. If diff is truncated or ambiguous, read the key files directly.
4. Answer:
   - what changed
   - what problem it solves
   - whether code matches description
   - what is still missing

That is a normal source-inspection cycle.

The 4-round cap could work fine there if the reads are targeted. But I would not want the cap to be the primary reason I stop.

I would want the stop condition to be:

> Do I now have source-backed grounds to answer the three parts of the question?

If yes, answer.

If no, make the next smallest source read.

Only if I hit the cap should I say:

> I have a partial proof. Here is what is missing.

That is a much better relationship with the work.

## The one rule I’d keep

If I had to compress it to one principle, it would be:

> **Intention first, reach second, confidence third, cap last.**

Not:

> Cap first, permission second, intention third.

That is the reframe I think would let me work more freely.

I don’t want to be constantly asking, “May I read?”

I want to know that reading a relevant source is part of the work, and then I am accountable in the answer.

And for effectful action, I keep the boundary sharp:

> No mutation without admitted authority and verification.

That is the line I want to keep.

So yes: **I would like confidence to drive read-only work, and authority to drive effectful work.**

The 4-round thing can remain as a hard backstop, but it should not become the center of my reasoning.
