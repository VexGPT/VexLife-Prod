## Current runtime truth

P1 is a generated **connected product surface**. Presentation does not own the underlying runtime
semantics.

```text
VexLifeWebP1RuntimeArtifacts
  -> current source-currentness projection
  -> current canonical Conversation projection
  -> current Context projection
  -> current frame-host / browser-context projection
  -> current Conversation Send route
```

Send preserves the current capability relationship:

```text
Send
-> Capability(conversation.send)
-> existing VexLife-Prod local service Send route
-> existing Conversation / Context / runtime owners
```

ContextShare is a local interaction with ContextReceipt. It controls whether an already-admitted
browser-context observation is included in the next current Send request; it does not become a
Conversation, prompt-selection, or provider owner.

Human page display and Vex page context are now explicitly separate relationships:

```text
BrowserViewport
  -> direct ordinary HTTP(S) navigation
  -> visible page retains its own URL/origin/site behavior
  -> browser-pane sandbox permits ordinary in-pane scripts/forms/popups/downloads
     without granting top-level VexLife navigation authority

Vex BrowserContext
  -> separate isolated context frame
  -> current admitted context-provider boundary
  -> not loaded merely because the human opened a page
  -> explicit Include page starts context acquisition
  -> current Send only when an exact current observation exists
```

Permanent:

```text
HUMAN PAGE DISPLAY != CONTEXT PROXY
VISIBLE PAGE != VEX CONTEXT CURRENT
HUMAN NAVIGATION SCOPE != VEX CONTEXT-ADMISSION SCOPE
```

The context frame remains isolated implementation topology and must not redefine what the human
Browser is allowed to display. It is lazy: opening a human page does not also fetch the page through
the context proxy. Explicit Include-page intent starts that separate acquisition. A page may therefore
be human-visible while Vex page context is truthfully unavailable.

Because the current web-hosted implementation cannot inspect an arbitrary cross-origin human frame,
the context receipt describes the context provider's separate rendering of the same entered URL; it
does not counterfeit that rendering as the exact DOM of the visible frame.

Direct human web display also does not grant local Product effect authority. The loopback service
accepts only its exact loopback Host, and browser-originated non-read requests must remain same-origin
with the Product presentation. Non-browser local clients may continue to omit browser provenance
headers.

```text
HUMAN WEB ACCESS != LOCAL PRODUCT EFFECT AUTHORITY
CROSS-ORIGIN PAGE != VEXLIFE SERVICE CLIENT
```

The current web-hosted presentation still uses an HTML iframe as its human renderer. Its human-frame
sandbox preserves ordinary in-pane interaction while withholding top-navigation authority from the
page; this is container protection, not origin virtualization. Sites may still deny iframe embedding, and a cross-origin child navigation performed inside that iframe does not expose
its exact new URL to the parent presentation. When the presentation cannot truthfully identify that
new page, it clears BrowserContext / Include-page state rather than carrying stale context. A later
native/browser-engine provider may replace this human rendering limitation without changing the
Conversation or BrowserContext ownership boundaries.

Conversation and Settings are alternate Companion presentations. Their view switch is presentation
state only and does not mint another product semantic-state owner.

Controls whose current backend effect is not admitted remain non-effecting rather than fabricating
capability. Home directory mutation, Continuity mode, Dream sync, Stop, and low-memory alert remain held.

Settings / Continuity renders the service's Memory projection (`GET /api/v1/memory`, owned by
`VexLifeMemoryFamily`; see `VEXLIFE-CONTINUITY-REALIGNMENT.md`) and the per-turn Memory inclusion
note. Continuity mode and Dream sync stay disabled as "Not available yet", with one line naming what
each will be in the predecessor's own terms (Home Bridge continuity modes; Dream Sync review), so the
label is not left to imply a meaning nobody owns yet.

Settings / Resources now consumes the read-only local-service current-state projection rather than
displaying a placeholder for Mac resource truth. The projection is formable independently of
`VexLifeProdLocalSetup`, so awareness does not first select/bind a model, recover a writer, acquire
bytes or establish a runtime. It does not convert observations into repair, model-selection,
low-memory-alert or runtime-lifecycle authority.


## Private mode

The Companion header shows whether the conversation is being kept: **Kept in your archives**
(ordinary) or **Private**. `VexLifePrivateModeFamily` owns that meaning and the Begin/End Controls;
`VexLifePrivateConversation` realizes them in the service.

~~~text
Go private      -> an in-memory private conversation opens; nothing is written
private message -> POST /api/v1/private/send: private system note + the Memory Vex already had +
                   this private conversation so far -> local runtime -> reply held in memory only
canonical Send  -> refused with 409 while private, so a private message can never become a kept turn
Keep something… -> Vex proposes one short note; only those exact words can be kept (POST note/keep)
Leave private   -> transcript dropped; runtime/vexlife-prod/continuity/private-intervals/<ref>.json
                   records only when, how many exchanges, and the kept notes
service restart -> an open private conversation is lost entirely
~~~

Archives shows each ended private conversation on its day as "Private conversation · not kept",
with its kept notes. Telling Vex about the gap in ordinary prompts is the next slice.

## Reply language and what Vex is told about the person

The header's Language orb chooses the language Vex replies in. The choice is a Home setting
(`runtime/vexlife-prod/settings/person.json`, `VexLifePersonSettings`) rather than a browser
preference, because Vex is given it on every message: one selected-language authority, as
VexArchitecture's localization law requires.

~~~text
GET/POST /api/v1/settings          replyLanguage (one of Vextreme's ten), with each language's own name
every ordinary turn                DirectPromptContext carries one VEXLIFE_PERSON_CONTEXT/v1 system block:
                                     reply language + private conversations from the last 14 days
                                     (at most 5: when, how many exchanges, kept notes)
receipt                            personContextIncluded / snapshot (EncodeDefault NEVER, so receipts
                                     without it keep their historical shape); shown in Settings
private turns                      told the reply language too
<html lang>                        follows the setting, so Speech chooses voices in that language
~~~

The workspace's own text is still English. Localizing it under VexArchitecture's string-catalog law is
the next slice, starting with onboarding, where the language is chosen first.

## Speech

The header's Speech orb carries the Vextreme Spiral FAB's Read Aloud behavior, ported rather than
loaded (no runtime dependency on Vextreme), and extended into speech for Vex as it talks. It opens a
popover beneath the orb:

~~~text
Speak Vex aloud     on: Vex's reply is read as it streams, sentence by sentence, tail on completion
Voice               Natural (Kokoro, English) or this Mac's own voices (other languages)
Read out thoughts   also read Vex's streamed thinking, before its reply
Speed · transport   play / pause / stop / previous / next; "Start here…" reads from any message
~~~

What it reads is the Conversation projection (or the private one), never the DOM. Speech never starts
before the person has turned it on or chosen where to start.

Privacy: Kokoro runs in a module Worker on this machine. The first use downloads `kokoro-js@1.2.1`
(jsDelivr) and `onnx-community/Kokoro-82M-v1.0-ONNX` (Hugging Face) once, and the popover says so.
The words themselves never leave the machine. System voices are limited to on-device ones
(`voice.localService`). If the natural voice can't load, this Mac's voice takes over and the person is
told. Settings persist per browser (`vexlife-prod.presentation.speech/v1`).

Speech follows the selected output language once Language becomes a Home setting (next slice). The
other unbound orbs (Journeys, Evolution) stay as they were: visibly held, not wired.
